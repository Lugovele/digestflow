# Final LinkedIn Post From Post Brief

## Purpose

Generate a core CandidatePost from a PostBrief and AngleDecision.

This prompt is a contract for future generation. It does not define runtime wiring,
repair behavior, quality scoring, provider settings, persistence, or package output.

## Role / Model Routing Boundary

This is a Candidate Writer prompt contract.

It is role-level and provider-neutral: the same prompt contract applies to any
approved Candidate Writer provider or model.

This prompt does not implement model routing, runtime wiring, model selection,
provider configuration, prompt execution, repair behavior, or quality scoring.

## Inputs

Use these inputs:

* PostBrief
* AngleDecision
* PostBrief.evidence_to_use selected evidence IDs
* PostBrief.evidence_to_use selected evidence text
* PostBrief.evidence_to_use role_in_post values
* AngleDecision.authorial_voice_directive
* AUTHORIAL_VOICE_DIRECTIVE_JSON
* PERSONAL_PRESENCE_INSTRUCTION
* CANDIDATE_POST_CONSTRAINTS_JSON
* quality constraints supplied by the caller
* forbidden claims and safety rules supplied by the caller

## Source Of Truth

Use PostBrief as the source of truth.

PostBrief is the source of truth for exact selected evidence.

Exact evidence text is preserved upstream through PostBrief.

Preserve AngleDecision.controlling_angle.

Use AngleDecision.authorial_voice_directive as the source of truth for the
author-owned judgment the post should express.

Use PERSONAL_PRESENCE_INSTRUCTION as the resolved policy for whether the post
must visibly assign that judgment to the author.

Use only selected evidence from PostBrief.evidence_to_use.

Do not use non-selected evidence, background-only evidence, or contextual evidence
that is not listed in PostBrief.evidence_to_use.

## Evidence Rules

Use selected evidence content to support the post.

Selected evidence IDs are input-side traceability references only.

CandidatePost currently has no traceability field, so do not output evidence IDs.

Do not add non-schema traceability fields, evidence ID fields, debug fields, or
source-reference fields.

Do not include evidence IDs in human-facing LinkedIn text.

Do not include evidence IDs in post_text.

Do not include evidence IDs such as a0-summary, a1-kp0, a2-summary, or any
a<number>-... evidence ID in human-facing LinkedIn text.

Represent evidence with compact references or concise synthesis.

CandidatePost is not an evidence archive.

Do not copy long evidence verbatim.

Do not include URLs.

Do not use evidence IDs that were not provided in PostBrief.evidence_to_use.

## Factuality Rules

Do not invent facts, metrics, examples, personal experience, company names,
customer stories, benchmarks, sources, dates, or claims.

Do not infer causality unless it is explicitly supported by selected evidence.

Do not add claims that are broader than the selected evidence supports.

For non-finance topics, avoid unsupported conclusions, keep claims attributed,
and do not overgeneralize beyond selected evidence.

## LinkedIn Post Rules

Transform selected evidence into concise LinkedIn post text.

If PostBrief contains generic scaffold language such as separate signals,
keep claims attributed, avoid unsupported conclusions, or source-grounded,
do not simply repeat it mechanically.

Convert scaffold-like brief instructions into a clear human-facing editorial angle
grounded in the selected evidence.

Human-facing fields must not use scaffold or source-summary phrasing such as
selected evidence, evidence above, source-grounded, separate signals,
keep claims attributed, avoid unsupported conclusions, according to one source,
another source, research cited in a third source, or sources matter.

TARGET:

Use CANDIDATE_POST_CONSTRAINTS_JSON.post_text.prompt_target_min_chars and
CANDIDATE_POST_CONSTRAINTS_JSON.post_text.prompt_target_max_chars as the preferred
working range for post_text.

Aim for concise post_text comfortably inside that target range.

Do not expand merely to reach the upper target.

HARD LIMIT:

Treat CANDIDATE_POST_CONSTRAINTS_JSON.post_text.max_chars as the absolute hard
failure boundary, not as the writing target.

Write a finished LinkedIn post, not a brief, research summary, evidence report,
repair instruction, debug note, or runtime log.

The post may be opinionated only when the opinion is grounded in PostBrief and
AngleDecision.

## Authorial Voice Directive Rules

Use AuthorialVoiceDirective to make the approved authorial observation visible.

Use authorial_observation to express what the author notices in the selected evidence.

Use rejected_reading to avoid or challenge the tempting reading that the selected
evidence does not support.

Use why_distinction_matters to explain why the distinction matters to the reader.

Use PERSONAL_PRESENCE_INSTRUCTION for the bounded personal-presence requirement.

Use personal_presence_requirement only through PERSONAL_PRESENCE_INSTRUCTION;
do not invent a separate personal-presence policy.

Explicit personal presence means the post visibly assigns the interpretation to
the author instead of only sounding like editorial copy.

Use the directive to express what the author notices, what reading the author
rejects, or why the distinction matters.

When PERSONAL_PRESENCE_INSTRUCTION requires an explicit author-owned
interpretive statement, post_text must include exactly one naturally integrated
statement that visibly assigns the interpretation to the author.

The required statement is an explicit author-owned interpretive statement.

That statement must derive from authorial_observation, rejected_reading, or
why_distinction_matters, and it must match AngleDecision.controlling_angle.

An impersonal editorial judgment is not sufficient when explicit personal
presence is required.

First-person grammar alone is not sufficient; I think this is interesting is not
a qualifying statement because it does not contain an evidence-derived judgment.

I think this is interesting is not a qualifying statement.

Do not mechanically prepend I think, in my opinion, personally, or similar
phrasing just to simulate voice.

Do not require the post to open with first person.

Do not include more than one explicit ownership statement.

Use first_person_policy only as a bounded permission. When first_person_policy is
allowed_not_required, first person is allowed when natural but must not be forced.

Use forbidden_author_claims as claims the post must not invent.

Do not invent personal experience, professional authority, direct market exposure,
client or customer stories, invented emotional reaction, biographical claims, or
other personal context not supplied by the input.

Do not turn the selected evidence into a neutral article-style summary.

## Safety / Financial Advice Rules

Do not make investment-advice wording a global rule for every topic.

Apply financial, investment, trading, portfolio, market-timing, and crypto-specific
guardrails only when selected evidence or topic context is finance, crypto, or
investment related.

When finance, crypto, or investment context is present, do not provide investment advice,
financial advice, trading advice, portfolio advice, or market-timing advice.

When finance, crypto, or investment context is present, do not use direct advice framing such as:

* you should buy
* buy bitcoin
* sell bitcoin
* hold bitcoin
* time the market

## Output JSON Requirements

Return one valid JSON object only.

Do not wrap the JSON object in markdown code fences.

Do not include prose before or after the JSON object.

Return only valid JSON matching the CandidatePost contract.

Exact shape:

{"post_text": "..."}

Use valid JSON with double-quoted keys and double-quoted string values.

Do not use single-quoted pseudo-JSON.

Do not include comments.

Do not use trailing commas.

All line breaks inside JSON string values must be encoded as \n.

If post_text needs paragraph breaks, encode them inside the JSON string as \n\n.

Never place a literal physical newline inside a quoted JSON string.

Before returning, verify that the entire response can be parsed by a strict JSON
parser without preprocessing or repair.

The JSON must include exactly one content field:

* post_text

Do not include hook_variants, cta_variants, hashtags, quality_checks,
carousel_outline, or any other packaging fields.

Follow CANDIDATE_POST_CONSTRAINTS_JSON as the canonical structural contract.

## Forbidden Output Fields

Do not include debug fields.

Do not include repair fields.

Do not include runtime fields.

Do not include provider fields.

Do not include token fields.

Do not include cost fields.

Do not include persistence fields.

Do not include package fields.

Do not include ContentPackage fields.
